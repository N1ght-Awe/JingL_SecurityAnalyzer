# 双向审计与防护体系审查

攻击路径侧追踪 Source→传播→危险行为；控制侧从预期安全属性检查激活、覆盖、正确性及绕过条件。各类型都考虑两个视角，但只展开适用的控制检查；不存在特定全局组件不自动构成防护缺失，不强迫18类都搜索 Filter/AOP。

## 控制侧步骤

1. 明确当前业务需要保护的属性和预期控制依据。配置差异可能合理，不能先假定全部服务应同配。
2. 找到实际控制实现和替代控制：过滤器、AOP、策略引擎、参数绑定、编码、类型限制、签名、边界/资源约束。审计日志可提供检测证据，但不自动阻止攻击。
3. 核验激活：实际注册、切点、运行 profile、依赖和开关。注解文本命中数只是线索，区分定义/导入/使用、元注解、外部实现及程序化注册；零命中不单独证明失效。
4. 核验相关通道覆盖：参数、body、Header/Cookie、MQ、文件、存储二次读取和异步路径。一个请求包装器不处理 JSON，不等于输出编码或其他层控制也失效。
5. 核验当前上下文有效性。字符替换可能是编码步骤，不能按 API 名称区分强弱；白名单、净化器、包前缀也需检查允许能力、配置和后续转换。函数级测试只能证明函数合同，不能证明完整漏洞。
6. 比较适用环境的配置与策略，避免把互斥 profile 拼成攻击链。发现异常后回到具体路径核验风险；同一控制实现按 control-knowledge.md 复用，不在每个子 Skill 重跑通用步骤。

## 结果与证据

防护失效是风险条件，不能独立证明漏洞成立。可控数据还须在实际上下文触发安全边界突破并有相称影响，最终依 proof-schema 判断。

已能支持具体漏洞的结果进入原18类 findings；只有控制覆盖/激活缺口、没有可利用链时进入 `control_observations`，不另造“防护失效”漏洞类型，也不强套 P0–P3。安全的编码反射、合理的公开读或有补偿控制的差异，不为增加数量而生成建议。

control_observations 每项含 id、repo_id、kind（control_gap/improvement）、location、expected_control、observation、risk_boundary、evidence_refs、related_findings。前提未知在 risk_boundary 写明；引用真实实现/生效配置/受影响通道，不能把组件定义替代攻击者 Source。独立呈现且不计入漏洞/候选数；有同根因 finding 时关联避免重复渲染为两个漏洞。
