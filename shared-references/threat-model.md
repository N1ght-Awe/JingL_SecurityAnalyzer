# 轻量威胁概览

在现有范围与画像步骤中建立，供候选发现、证明目标与报告共用。不另开一轮扫描，不新增威胁模型专用Agent，不重复复制资产清单。先写当前源码能够支撑的边界，深审遇到新事实时更新同一对象。

只回答四件事：系统做什么；哪些主体能控制哪些输入或操作；他们与受保护资产之间应守住什么规则、实际由哪里防护；哪些条件尚不清楚。优先选与实际授权范围相关的入口、权限、数据处理、执行和传输边界，不为了凑类型列举通用攻击。

沿代表性输入追到控制和敏感操作，再从消费者反查实际配置、参数、注册及返回值。区分源码事实、用户提供的部署/业务背景、推断和未知。不能由函数名、注解名、localhost或“内部系统”推定安全，也不能把危险API直接列成漏洞。威胁假设只指导检查，发现必须继续遵循八维证据和监督门槛。

## 只增加一个报告对象

`threat_model` 含四个键：

- `summary`：一至两句系统用途及本次范围。
- `actors`：简短字符串数组，说明主体及初始可控输入/权限；未知则留空并写入assumptions。
- `boundaries`：实际边界数组。每项 `name`（如“普通租户 → 导出服务”）、`asset_ids`（引用已有assets）、`rule`（应始终成立的安全要求）、`control`（实际控制位置/缺口）、`evidence`（复用state/summary/refs，state限observed/inferred/missing）、`finding_ids`（关联当前候选，无则空）。不新增第二套资产、候选ID或结论状态。
- `assumptions`：尚未核实的部署条件、业务政策和证据缺口；注明来源。不存在问题填空数组，不编造生产环境。

observed表示已审查描述所依赖的证据，不表示防护必然有效；观察到无控制也可observed，须有范围和源码依据。rule来自用户给定政策时明确归因，源码未能证明的部署/权限假设保留在assumptions。未找到边界时必须说明画像缺口，不能把空表解释为无风险。

已有候选关联对应边界；关联只是导航，不增加漏洞数量、不替代证明。没有候选的边界不自动变成“安全”。新报告在漏洞扫描报告开头展示这张简表，完整证据仍用原JSON和附件，避免另交一份重复长文。展示尽量紧凑，但不能为页数上限删除真实边界或缺口。
